# Nexa Download Manager — independent deep audit

**Date:** 2026-09-12
**Scope:** whole tree — Qt desktop app, native host, both browser extensions, Node/Express backend, React site + admin, CI.
**Method:** every finding below was read out of the current source and is cited by file and line. Nothing is carried over from the existing audit documents; where those documents already cover something, it is marked **[known]** and only its current status is reported.

## Status — 2026-09-12, same day

Every finding below has been fixed in the tree except **W4**, which is a documented product trade-off left as is. Fixes were made without a C++ toolchain on the machine, so the desktop changes are reviewed and structurally checked but **not yet compiled**; CI's Linux/Windows/macOS jobs are their first build. ## Desktop app

### <a id="d1"></a>D1 — Unknown-size downloads fail whenever the server answers 206 · **High**

`src/core/SegmentDownloader.cpp:221-230`

```cpp
if (status == 206) {
    ...
    if (total >= 0 && m_requestEnd >= total)
        return QStringLiteral("server returned an out-of-bounds byte range");
```

A download whose size the probe could not establish is built as a single **open-ended** segment:

```cpp
// src/core/DownloadTask.cpp:1014
s.end = (total > 0) ? (total - 1) : (qint64(1) << 62);
```

so `m_requestEnd == 2^62` and the worker asks for `Range: bytes=0-4611686018427387904`. When the server answers `206` with a real `Content-Range: bytes 0-N/TOTAL`, the bound check reads `2^62 >= TOTAL` — **true for every real file** — and the segment is failed. `retrySegment` repeats it identically five times, then the download errors with *"segment 0: server returned an out-of-bounds byte range"*.

This kills precisely the case the surrounding code was written for. The comment at `SegmentDownloader.cpp:154-159` explains that Drive, GitHub artifacts and AI-export endpoints answer the `bytes=0-0` probe without a length and only reveal the size on the live transfer — and `onMetaData` computes `emit sizeDiscovered(total, status == 206)` (line 206) while `DownloadTask::onSizeDiscovered` clamps the single open-ended segment (line 1250). **Both are unreachable for a 206**, because `responseValidationError()` runs first (line 165) and aborts.

Fix: exempt the open-ended case, which the class already tracks.

```cpp
if (!m_openEndedRequest && total >= 0 && m_requestEnd >= total)
    return QStringLiteral("server returned an out-of-bounds byte range");
```

`tests/RangeIntegrityTest.cpp` covers the range-ignoring 200 and the 403 error-page cases but has no open-ended-segment case; a regression test belongs with the fix.

### <a id="d2"></a>D2 — HLS/DASH shows no progress and finishes reporting "1 byte" · **High**

`src/grabber/HlsGrabber.cpp:133`, `:527-593`, `:609`

`HlsGrabber::start()` ends with an unconditional `muxViaFfmpegDirect()`. That function starts ffmpeg with **only** `finished` and `errorOccurred` connected — no stdout/stderr handler — and never touches `m_bytes`. The only other `emit progress` in the class sits in the per-segment path, which is unreachable ([D3](#d3)).

So the sole progress signal a stream job ever emits is the one fired when ffmpeg exits:

```cpp
// :609 — m_bytes is always 0 on this path
emit progress(m_id, m_bytes > 0 ? m_bytes : 1, m_bytes > 0 ? m_bytes : 1, 0.0);
```

For the entire download the row shows 0 B, no total, no speed, no ETA and the static detail `"downloading via FFmpeg"`; on completion it reports **done = total = 1 byte**. `DownloadEngine::cacheProgress` stores that, so the phone dashboard (`WebServer::downloadsJson`) reports it too.

ffmpeg's stderr is also never drained by the application, so QProcess buffers the whole progress stream in memory for the life of the download.

The fix and the missing feature are the same work: connect `readyReadStandardError`, parse ffmpeg's `size=`/`time=`/`bitrate=` stats (or pass `-progress pipe:1`), and feed `m_bytes` plus a real `progress` signal.

### <a id="d3"></a>D3 — The per-segment HLS engine is dead code; a shipped setting does nothing · Medium

`fetchPlaylist`, `onPlaylistFetched`, `pumpDownloads`, `startSegmentRequest`, `onSegmentFetched` and `startMux` (≈350 lines, `HlsGrabber.cpp:152-525`) are reachable **only from each other**. `start()` never enters the cluster. Their hardening — the `m_publicNetworkOnly` checks at `:154` and `:441`, the redirect scheme validation at `:192` — never executes.

The user-visible consequence is a setting that lies. `m_concurrency` is read only by the dead `pumpDownloads()` (`:384`), yet it is:

- a Settings spinbox, range 1–64, default 16 — `src/ui/SettingsDialog.cpp:245-248` ("HLS stream connections"),
- persisted and reloaded — `SettingsDialog.cpp:89`, `:490`,
- pushed into every grabber — `src/core/DownloadEngine.cpp:610`,
- and multiplied into a headline metric tile: `const int threads = active * qMax(1, m_engine->streamConcurrency());` — `src/ui/MainWindow.cpp:996`, which renders "↑ N threads" from a number that controls nothing.

Either restore the per-segment path behind the setting, or delete the dead code, the spinbox and the fabricated metric.

### <a id="d4"></a>D4 — Cookie-authenticated HLS streams can no longer be downloaded · Medium

`src/grabber/HlsGrabber.cpp:560-570` strips `Cookie`, `Authorization`, `Proxy-Authorization`, `X-Api-Key` and `X-Csrf-Token` before handing headers to ffmpeg. Keeping secrets out of a subprocess's argv is right — argv is readable by any process on the machine.

But this is now the only path, and the dead per-segment path (`scopedHeaders` at `:568` vs `:163`) was the one that carried them. A login-gated `.m3u8` therefore 403s. The engine still merges domain-scoped auth into the grabber (`DownloadEngine.cpp:606-608`), so supporting it is clearly still the intent.

ffmpeg accepts headers on stdin via `-headers` only as an argument, but the cookie can be passed safely through a file (`-cookies` for the HTTP protocol, or a `-headers` value written to a 0600 temp file and referenced) — or by restoring the per-segment path for authenticated hosts.

### <a id="d5"></a>D5 — `If-Range` on fresh downloads; a 206 without an echoed validator fails the download · Medium

`src/core/DownloadTask.cpp:1129` sets the validator on **every** worker, including segment 0 at offset 0. `SegmentDownloader::onMetaData` then requires the response to echo it:

```cpp
// src/core/SegmentDownloader.cpp:171-180
if ((m_seg.start + m_seg.done > 0 && status == 200) ||
    responseValidator.isEmpty() || responseValidator != m_ifRangeValidator) {
    m_validatorMismatch = true;
```

RFC 7232 says a 206 **SHOULD** carry the ETag, not MUST. A server or CDN that omits it on partial responses fails every segment with *"remote object changed during resume"* — a message that sends the user looking for a problem that does not exist. nginx, Apache, S3 and CloudFront all send it, so this is a long-tail failure, but the failure mode is total and the diagnosis is misleading.

Treat a missing validator in the response as "cannot verify" (proceed, or proceed only at offset 0) rather than as "changed".

### <a id="d6"></a>D6 — `fetchTorrentFile` replays captured cookies across a cross-host redirect · Medium

`src/core/DownloadEngine.cpp:830-842`

```cpp
for (const auto &h : headers)
    req.setRawHeader(h.first, h.second);          // includes Cookie / Authorization
req.setAttribute(QNetworkRequest::RedirectPolicyAttribute,
                 QNetworkRequest::NoLessSafeRedirectPolicy);   // Qt follows automatically
```

Qt re-sends the same raw headers to the redirect target, so a `.torrent` URL that 302s to another host receives the user's session cookie for the original site.

Every other network path in the app avoids exactly this. `DownloadTask` uses `ManualRedirectPolicy` and re-scopes credentials per hop (`DownloadTask.cpp:69-88`, `:645-672`); `HlsGrabber` filters through `scopedHeaders`; `DownloadEngine::resolveName` explicitly drops `cookie`/`authorization` before its own redirect-following probe (`:997-1002`). This one call site is the exception.

Fix: strip sensitive headers here too, or switch to manual redirects and reuse `sameCredentialScope`.

### <a id="d7"></a>D7 — Whole-file SHA-256 on the GUI thread for every download · Medium · **[known]**

Already recorded in `docs/issues.md:270`; re-confirmed unfixed. `DownloadTask::checkAllComplete` (`:1476`) and `finalizeShort` (`:1440`) both call `computeSha256()` unconditionally, and `computeSha256` reads the entire file before it ever consults `m_expectedSha256` (`:1501-1536`). On the single-threaded design this freezes the window *and stalls every other active download* for the duration, for no benefit unless a hash was supplied — which only the updater does (`MainWindow.cpp:928`, `:1187`).

### <a id="d8"></a>D8 — Dashboard re-executes the first request when a client pipelines or splits · Low

`src/web/WebServer.cpp:273-295`. `onReadyRead` appends to the per-connection buffer and parses from offset 0, and `dispatch()` never consumes the bytes it just handled. The buffer is only ever discarded when the connection is torn down.

So if a client's second request arrives as a separate `readyRead` before the socket finishes closing, the **first** request is parsed and dispatched a second time (and the second request is never seen). `POST /api/add` would queue the download twice.

Fix: `buf.remove(0, bodyStart + contentLength)` after a successful parse — or, since every response is `Connection: close`, stop reading from the socket once a request has been dispatched.

Unrelated but adjacent: the comment at `:369` says "The CORS headers ride on every response", but `sendResponse` (`:529-544`) emits none. The `OPTIONS → 204` handler therefore cannot satisfy a real preflight. Harmless today (the dashboard is same-origin, and no CORS headers is the safer state) — but the comment should go or the headers should be added.

### <a id="d9"></a>D9 — `addRemoteDownload` bypasses the job cap · Low

`src/core/DownloadEngine.cpp:1289-1306` builds a `DownloadTask` directly instead of going through `addDownload`, so it skips:

- `kMaxTrackedJobs` (10 000) — `:398-403`. `addRemoteBatch` caps a *single* call at 10 000 items, but nothing caps the total across calls, so a token-holding client can grow the task table without bound.
- the `m_confirmBeforeStart` hold.
- the Pro auth-site gate — **[known]**, `docs/issues.md` Issue 4, bypass #6. Still open.

Routing this through `addDownload` closes all three at once, which is what Issue 4's Tier 1 item 3 already recommends.

### <a id="d10"></a>D10 — `list-formats` blocks the GUI thread and spawns unbounded processes · Low

`src/ipc/IpcServer.cpp:399-528`

- `proc->waitForStarted(3000)` (`:524`) is a synchronous wait on the GUI thread. Everything — every active download, every repaint — stops for up to three seconds when yt-dlp is slow to exec (cold cache, on-access AV scanning on Windows).
- Nothing limits concurrent `list-formats` requests. Each allocates a `QProcess` parented to the server; a peer that sends N requests gets N yt-dlp processes.
- A non-zero exit is not checked: `finished` parses whatever was captured and replies `{"ok":true}` with empty `qualities` (`:419-496`), so a yt-dlp failure looks to the extension like "this video has no formats".

The IPC socket is user-scoped (`QLocalServer::UserAccessOption`, `:67`), so this is a robustness issue rather than a privilege boundary — but any code running as the user, including a compromised extension, reaches it.

### <a id="d11"></a>D11 — Linux credential store blocks startup for up to 7 s · Low

`src/license/CredentialStore.cpp:67-90` shells out to `python3 -c <secretstorage script>` with `waitForStarted(2000)` + `waitForFinished(5000)`. That runs from `LicenseManager::start()`, which `main.cpp:220` calls **before the window is shown**. A machine without `python3` or `secretstorage` pays 2 s on every launch; a locked keyring can pop a system unlock prompt inside the 5 s window; and `writeLicenseKey` failing is why the status line has a *"this session only; OS credential store unavailable"* branch (`LicenseManager.cpp:318`).

Reading the key is not needed before the first paint. Defer it to a single-shot timer after `show()`, or move it off the GUI thread.

### <a id="d12"></a>D12 — `clearCache()` also deletes the device seed · Low

`src/license/LicenseManager.cpp:578-582` does `settings.remove("license")` — the whole group, which includes `license/deviceSeed` (`:25`). On machines that fall back to the generated seed because they have neither a usable MAC nor a `machineUniqueId` (containers, some BSDs — `:127-136`), any cache clear changes `deviceFingerprint()` and therefore consumes a **new seat**. `clearCache()` is called on every rejection, revocation and deactivation.

Remove the four cached keys by name instead.

### <a id="d13"></a>D13 — Ad title and body render as Qt rich text · Low

`src/ui/AdBanner.cpp:94-97` assigns server-supplied strings with `QLabel::setText` and never calls `setTextFormat`. Qt defaults to `Qt::AutoText`, so `mightBeRichText()` turns anything containing markup into HTML. `setTextFormat` appears exactly once in the tree — `FirstRunWizard.cpp:39`, deliberately, on app-owned strings.

QLabel will not fetch remote resources, so the impact is markup/layout injection by whoever controls the ad feed rather than a network leak. One-line fix on `m_title`, `m_body` and `m_cta`:

```cpp
m_title->setTextFormat(Qt::PlainText);
```

### <a id="d14"></a>D14 — `NEXA_UPDATE_URL` is an unguarded override on the code-execution path · Low

`docs/issues.md` Issue 4, Tier 1 item 1 lists `NEXA_LICENSE_API_URL`, `NEXA_ADS_API_URL` and `NEXA_ALLOW_INSECURE_LICENSE_API` for removal from release builds. **`NEXA_UPDATE_URL` is not on that list** and is the one that ends in `QProcess::startDetached(installer)`.

`src/core/UpdateChecker.cpp:35-41, 70-74` accepts any `https` URL *or* plain `http://localhost` / `http://127.0.0.1`. The installer URL it returns must be `https` (`:107`), so this is not a remote attack — but it belongs in the same fix as the other three, at higher stakes.

Two related weaknesses on the same path:

- `MainWindow::offerInstallUpdate` decides whether the download was verified by **substring-matching the status text**: `m_stateDetail.value(id).contains("verified")` (`MainWindow.cpp:1465`). `DownloadTask::hashVerification()` is the authoritative source and is right there.
- When the feed carries no `sha256`, `setExpectedSha256` is never called (`MainWindow.cpp:926-928`) and the installer is launched with no integrity check beyond TLS. The feed should be required to carry a checksum, and the install offer refused without one.

### <a id="d15"></a>D15 — Mid-transfer cross-host redirects fail the segment · Low

`src/core/SegmentDownloader.cpp:385-395` requires `sameHost` for any 3xx during a transfer and otherwise fails with *"unsafe or looping range redirect"*. The probe resolves the initial chain, so segments normally start on the final host — but a signed CDN URL that expires mid-download and re-redirects (common on long multi-gigabyte transfers) kills the segment instead of following the hop with credentials stripped, which is what `DownloadTask` does on the probe path.

## Website and backend

The backend is in good shape: `verifyTyped` is used consistently (`utils/jwt.js:41-73`), Google ID tokens are fully verified including `email_verified` (`utils/googleAuth.js:92-103`), the Stripe webhook returns 500 so Stripe retries (`routes/webhooks.js:174-179`), `express.json` is capped at 1 MB (`app.js:29`), release uploads stream to disk with an extension allowlist and containment checks (`utils/releaseFiles.js`), and `config/env.js:136-162` refuses to boot in production without real secrets, HTTPS origins, `ADMIN_ALLOWED_IPS` and an explicit `TRUST_PROXY`. No `dangerouslySetInnerHTML` anywhere in the site or admin.

### <a id="w1"></a>W1 — One refresh-token slot per user · Medium

`users.refresh_token_hash` is a single column (`models/User.js:20-22`), and `/login`, `/google` and `/refresh` all overwrite it (`routes/auth.js:96`, `:182`, `:221`).

Consequences:

- Signing in on a second device **silently invalidates the first device's session**. For a product that sells 1-seat and 5-seat plans and has a "your devices" page, that is a visible defect.
- Two concurrent refreshes race — whichever writes second wins and the other tab is logged out. The SPA refreshes on every full page load (`middleware/rateLimiter.js:73-77` exists precisely because that is frequent), so this is reachable in normal use.

Fix: a `sessions` table keyed by token hash (device label, created/last-used, revoke-one and revoke-all), which the devices page can then surface.

### <a id="w2"></a>W2 — `/auth/refresh` and `/auth/verify-email` carry no rate limiter · Low

`routes/auth.js:212` and `:194`. Every other auth route has `authLimiter`; these fall back to the global 1000/15 min. Guessing a 48-byte random refresh token is not feasible, so this is an unauthenticated DB-load amplifier rather than an auth weakness. `adminRefreshLimiter` (120/15 min) already exists and is the right shape to reuse.

### <a id="w3"></a>W3 — Licence validation is 10/hour per IP · Low

`middleware/rateLimiter.js:37-41`, keyed on `req.ip`. Behind a shared egress address — an office, a campus, CGNAT — the eleventh activation in an hour is refused, and Team plans are exactly the customers most likely to sit behind one. The heartbeat correctly uses the general limiter, so only `/validate` is affected; consider keying on `license_key + ip` with a per-key allowance, or raising the ceiling.

### <a id="w4"></a>W4 — Login distinguishes "no account" from "Google-only account" · Low

`routes/auth.js:84-86` returns 409 `PASSWORD_NOT_SET` where an unknown address returns 401. The trade-off is documented in the code and the UX argument is fair, but it is an account-existence oracle for any address an attacker can guess.

### <a id="w5"></a>W5 — `User.update` / `Ad.update` interpolate the column name into SQL · Low (fragility)

```js
// models/User.js:57-68, models/Ad.js:51-62
const col = k.replace(/[A-Z]/g, (m) => '_' + m.toLowerCase());
sets.push(`${col} = ?`);
```

The key — not the value — goes straight into the statement. Every current caller passes hardcoded keys or a Zod-parsed object (Zod strips unknown keys, so `Ad.update(id, req.body)` at `routes/admin.js:691` is safe **today**). There is no live injection. But a single `.passthrough()` on a schema, or one new caller that forwards raw input, turns it into one — and the code gives no signal that the key is trusted. Add an explicit column allowlist per model.

## Tests and CI

### <a id="t1"></a>T1 — `ExtensionContentTest.js` never runs in CI and self-skips to a pass · Medium

`CLAUDE.md` documents `node tests/ExtensionContentTest.js` as part of the suite (the on-video button and quality dropdown — 14 KB of tests). `.github/workflows/build.yml:882` runs only the other two:

```yaml
node tests/ExtensionProviderConfigTest.js && node tests/ExtensionSettingsTest.js
```

And run locally without the frontend's `node_modules`, it reports success:

```
$ node tests/ExtensionContentTest.js
Extension content tests skipped — jsdom not installed (cd ndm-website/frontend && npm ci)
exit=0
```

So even adding it to CI would not help unless jsdom is installed first. The backend job already solves this exact problem correctly — `build.yml:818-824` greps the output and fails the build when a suite reports skips. Apply the same guard here.

(The other two tests pass: `Extension provider config tests passed`, `Extension settings tests passed`.)

### <a id="t2"></a>T2 — Translation extractor · Medium · **[known]**

`docs/issues.md` records that `tools/extract-translations.py` truncates multi-line `tr()` calls. Still unfixed, and there are two more defects in the same regex:

- `TR_RE.findall(line)` runs **per line** and returns every literal on it, so a same-line `tr("a" "b")` produces **two separate msgids** — not one truncated one. Qt looks up `"ab"`; neither entry can ever match.
- Three-argument plural calls (`tr("...%n...", nullptr, n)`) are emitted as ordinary messages with no `numerus="yes"` (`:79-107`), so plural forms cannot be translated at all.

No user impact yet — every `translations/*.ts` reports 0 translated — but this must be fixed before any translation work begins, or the strings that most need translating are the ones that cannot be.

## Performance

### <a id="p1"></a>P1 — The extension opts every request in the browser into `extraHeaders` · Low

`extension-chromium/background.js:626-632` registers `onBeforeSendHeaders` on `<all_urls>` with `["requestHeaders", "extraHeaders"]`. The listener itself exits immediately for hosts without `captureRequestHeaders` (`:572`), but in Chromium the `extraHeaders` opt-in disables network-stack fast paths for **every request in the browser**, not just the ones the listener acts on. Narrowing the listener's `urls` filter to the handful of provider hosts that set `captureRequestHeaders` removes the cost with no functional change.

The extension is otherwise carefully built: `onMessage` is gated on `sender.id !== chrome.runtime.id` (`:979`), there is no `onMessageExternal` surface, incognito requests are never captured (`:572`), captured headers are TTL-bounded and size-capped (`:521-527`), and `downloads.onCreated` has three independent guards against adopting the browser's restored downloads (`:888-892`).

### <a id="p2"></a>P2 — Full segment-table rewrite every ~2 s per active download · Low

`src/core/Database.cpp:145-212`. `saveTask` deletes and re-inserts **all** segment rows inside a transaction, and re-prepares the INSERT inside the loop (`:192-195`). With 32 segments (`preferredSegmentCount` for files ≥ 100 MB) across several concurrent downloads, that is a steady stream of synchronous SQLite work on the GUI thread every two seconds (`DownloadTask.cpp:1617-1620`). WAL + `synchronous=NORMAL` keep it cheap, but the statement should be prepared once outside the loop, and an UPDATE-by-`(download_id, idx)` would avoid the churn entirely except when the layout actually changes.

## What is genuinely well built

Worth stating, because several of the findings above are "this good pattern is missing in one place" rather than "this is unsafe":

- **Range integrity.** `responseValidationError()` refuses a 200 to a resumed request, a wrong or out-of-bounds `Content-Range`, and a 416; `pump()` refuses to write any body that is not a 200/206 so an error page can never land at a segment offset; a short write is treated as a retryable failure rather than a silent gap. `tests/RangeIntegrityTest.cpp` pins two of these. D1 is a bug *in* that machinery, not an absence of it.
- **Credential scoping.** Sensitive headers are enumerated in one place and dropped on any cross-host hop unless the provider registry explicitly approves the sibling (`DownloadTask.cpp:41-88`). Redirects are followed manually everywhere it matters, precisely so credentials can be stripped first. D6 is the single exception.
- **Untrusted-input discipline at the IPC boundary.** `IpcServer` validates scheme, host, public-network reachability, auth-domain shape and bearer-token charset, and explicitly refuses an `authCookiesFile` path so a local peer cannot make the app read `~/.ssh` (`IpcServer.cpp:341-351`). Frame lengths are bounded with 64-bit math.
- **Fail-closed entitlements.** `Entitlements` defaults to the Free set, so a build that is offline before its first validation gates rather than leaks.
- **Backend config validation.** `config/env.js:136-162` is the strongest part of the website: production cannot boot with dev secrets, duplicate JWT secrets, a default MySQL password, HTTP origins, an unset `TRUST_PROXY` or unrestricted admin IPs.
- **The native host.** Bounded frames, ownership and symlink checks before launching the engine, and a reply relayed only after a complete well-formed frame.
